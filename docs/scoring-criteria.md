# Описание кейса

## Суть задачи

Разработать прототип бота-помощника, который берёт на себя роль project-менеджера. Работает в фоне, сам следит за чатами и встречами, ведёт задачи и напоминает.

**Кейсодержатели:** Егор Олегович Орёл (зам. директора, фонд Сколково / агентство «Сапфир»), Даниил Волков (руководитель разработки).

---

## Обязательный функционал

1. **Интеграция с Telegram** — бот добавляется в командный чат, читает переписку, распознаёт задачи, дедлайны, ответственных.
2. **Присутствие на встречах** — подключается к Яндекс Телемосту (в идеале — к любому сервису через захват звука), слышит устные договорённости, пишет саммари, выносит задачи на канбан.
3. **Ведение канбан-доски** — интеграция с YouGile. Автоматически создаёт, двигает и закрывает карточки задач.
4. **Проактивные напоминания** — пишет в чат или лично: «Задача X через 2 часа», «Вы не обновили статус». Вечером присылает каждому его список задач.
5. **Минимальное ручное управление** — всё взаимодействие — только подтверждения. Бот сам извлекает контекст.

**Дополнительные возможности (усилят решение):** трекинг скорости и качества задач, личный кабинет, рекомендации по развитию, геймификация (ачивки, RPG), общая база знаний команды, адаптация под госуправление.

---

## Ключевые инсайты с первой встречи с кейсодержателем

- **Платформа — Telegram** (основной канал). MAX-бот недоступен физлицам, поэтому Telegram выбран как окно взаимодействия.
- **Канбан — YouGile** (он же Weeek). У Trello ограничения по аккаунтам.
- **Встречи — приоритет Яндекс Телемост**, но любой канал приветствуется. Онлайн-подсказки в реальном времени — фича «со звёздочкой», постфактум — приоритет.
- **Вечерняя синхронизация** — каждый скидывает сделанное за день, бот сверяет с канбаном, двигает карточки, подсвечивает тех, кто не отчитался.
- **Реалтайм во время звонка** — лучше постфактум: подвести итоги после разговора и распределить задачи.
- **Обязательные поля карточки** — название, дедлайн, исполнитель, краткое описание.
- **Ролевая модель** — менеджер, отвечающий за бота; несколько чатов, разные роли.
- **Стиль общения бота** — простой, без сленга, использовать слова, реально произнесённые людьми.
- **Ограничения по API** — нет (OpenAI, Claude — всё разрешено). После хакатона модель можно заменить.
- **Безопасность** — команда осознаёт, что при использовании открытых API данные обрабатываются вовне. Табу — заведомо вредный функционал.

**Главные приоритеты MVP (слова Егора Орла):**
> Telegram → Яндекс Телемост → канбан (YouGile) → проактивные напоминания → вечерний синк → минимум ручного управления.

---

## На что обращают внимание при оценке

- Рабочий MVP — бот создаёт задачи в канбане из чата.
- Автономность — как редко нужно вмешательство человека.
- Качество распознавания (текст + голос).
- Удобство пользования для команды заказчика.
- Наличие дополнительных фич.

# Критерии оценки — 1 этап (Problem & Solution Validation)

## Итого: 60 баллов (6 критериев × 0–10)

---

## 1. Понимание проблемы — 0–10 баллов

Насколько команда разобралась в задаче трека и её ограничениях.

| Балл | Что показывает команда |
|------|----------------------|
| 0–2 | Проблема не описана или список очевидных фактов |
| 3–4 | Проблема названа поверхностно, без ограничений трека |
| 5–6 | Проблема описана, есть следствия, но нет понимания почему именно этот кейс сложен |
| 7–8 | Чёткий root cause, ограничения трека учтены, есть боль конкретного пользователя |
| 9–10 | + данные/цифры, разбор барьеров внедрения, понимание почему аналогов нет |

---

## 2. Целевая аудитория и ценность — 0–10 баллов

Понятно ли, для кого создаётся решение и какую пользу оно приносит.

| Балл | Что показывает команда |
|------|----------------------|
| 0–2 | «Все» или одна строка |
| 3–4 | Список сегментов без ценности |
| 5–6 | Сегменты + общая польза |
| 7–8 | Конкретные роли, конкретная ценность для каждой, user journey |
| 9–10 | + приоритизация сегментов, измеримые выгоды, цитаты из интервью |

---

## 3. Концепция решения — 0–10 баллов

Насколько логично предложенное решение отвечает на проблему.

| Балл | Что показывает команда |
|------|----------------------|
| 0–2 | «Сделаем бота» |
| 3–4 | Функции перечислены, логика связи с проблемой отсутствует |
| 5–6 | Решение описано, связь с проблемой есть, архитектура не объяснена |
| 7–8 | Логичная цепочка проблема → решение, обоснование ключевых выборов |
| 9–10 | + сравнение альтернатив, обоснование отказа, уникальность подхода |

---

## 4. Определение MVP — 0–10 баллов

Выбран ли реалистичный объём работ для хакатона.

| Балл | Что показывает команда |
|------|----------------------|
| 0–2 | MVP не определён или равен всему продукту |
| 3–4 | Список фич без приоритизации |
| 5–6 | MVP выделен, но нет критериев «сделано» |
| 7–8 | MVP реалистичен, зафиксированы этапы, понятно что выброшено из scope и почему |
| 9–10 | + критерии готовности, таймлайн, явная граница MVP / nice-to-have |

---

## 5. Реализация ключевого функционала — 0–10 баллов

Прогресс по созданию основных возможностей MVP.

| Балл | Что показывает команда |
|------|----------------------|
| 0–2 | Ничего не сделано |
| 3–4 | Есть скелет проекта / заготовки |
| 5–6 | Работает 1–2 ключевых компонента |

## 6. Техническая реализуемость — 0–10 баллов

Отсутствие критических рисков и возможность довести решение до демо.

| Балл | Что показывает команда |
|------|----------------------|
| 0–2 | Стек не определён или нереалистичен |
| 3–4 | Стек выбран, но критические риски не закрыты |
| 5–6 | Стек адекватный, риски признаны |
| 7–8 | Риски идентифицированы и митигированы, команда знает стек |
| 9–10 | Уже задеплоено, демо-среда готова, нет блокеров |
